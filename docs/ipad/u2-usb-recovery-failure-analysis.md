## Why v1–v3 differ from v4

The most informative comparison is v3 versus v4. Both began with a 16-field original live description, used the same 3-second normal worker lifetime, called `SetDescription` followed by the explicit bounded bus cycle, and passed current-boot external prechecks. The selected description construction path changed: v3 rebuilt from defaults and patched four visible fields; v4 cloned the active controller description. Only v4 recovered all externally checked functions. The constructor path is the main **source-level design difference** between these normal trials, but they ran on separate boots and v4 passed only once; this does not prove the clone path caused the pass or is reliable. Adding `GoOffAndOnBus` by itself was insufficient (v2 versus v3).

The exact internal reason is not exposed by the retained evidence. A new read-only in-memory probe on a recovered stock boot found that the defaults-built and controller-cloned objects each returned nine interface arrays and those arrays were `CFEqual`. After adding the four known live-only values to the defaults object's info dictionary in memory, its 16-field dictionary was also `CFEqual` to the clone's. Whole-description `CFEqual` returned false, but two independently created controller clones also returned false, so that operation **cannot** diagnose hidden function binding here. These results rule out a simple missing interface-name list or visible field mismatch. They do not prove that defaults-built and cloned objects carry equal opaque references, runtime function state, or kernel behavior when published. The probe used no `SetDescription`, bus cycle, or file write, and full external USB/NCM checks passed before and after.

The v4 pass is limited. Its live registry description retained `AllowMultipleCreates=true` as a 17th field, and 14 USB string indices were renumbered while their resolved values remained equal. It passed semantic external function recovery and receipt confirmation; it did **not** restore the exact 16-field live shape required by the stricter U2 checklist. The publication shim inserts that flag before every `SetDescription`, including recovery.

## Why v5 may differ from v4

V5 changed two variables at once:

1. **Recovery timing.** The v4 normal worker remained alive for 3 seconds after publication. The v5 fault client called `os._exit(17)` immediately after receiving `OK published`, and the watchdog's `workerClosed` path synchronously called `recover()` with no first-enumeration readiness check (`u2-native-noop-trial-client-v5.py`, `NativeUSBWatchdogService.swift`, `USBRestoreCoordinator.swift`). The `OK published` reply follows API success, not an external arrival. Both publication and recovery call `SetDescription` and `GoOffAndOnBus(1000)` in `USBRestoreControllerShim.c`. The [Apple-authored historical controller header](https://github.com/nabla-c0d3/iphone-dataprotection/blob/master/ramdisk_tools/IOUSBDeviceControllerLib.h) describes a delayed return to the bus after `GoOffAndOnBus`; a successful return from the API does not document completed host enumeration. In v4, the first Mac arrival preceded the second termination by only 35 ms; in v5, no arrival was recorded. The v5 journal reached `awaitingVerification` near the first termination. An early second bus transition is therefore a concrete, source-backed failure mechanism, but the retained trace lacks a timestamp for the recovery call and cannot prove the transition preceded a would-be first arrival. A Mac-only fake-controller test passes with the offline v6 candidate's five-second delay for both worker death and watchdog restart. It proves the delay is taken, not that this iPad enumerates or recovers.
2. **Starting opaque state.** V4 began from the original stock description. V5 began from v4's post-replacement 17-field state. Its external precheck passed and its journaled 16-field dictionary is value-equal to the original pre-v4 dictionary; the extra live field was only `AllowMultipleCreates`. Nonetheless, `CreateFromController` may clone opaque state that changed during v4. The v5 in-memory validator checked visible info values, not a complete internal function-binding equivalence.

The v5 Mac lifecycle window had no arrival, and the iPad later read `disconnected/onbus=no/config=0` while Wi-Fi SSH and power remained. Mac USBMux logs recorded failures/detach without a specific controller error. On this recovered iPad, no accessible `log`, `syslog`, or `dmesg` CLI was found in the checked paths to retrieve a prior-boot controller trace. The retained data cannot separate timing from the post-v4 opaque state. Claiming that either alone caused v5 would overstate the evidence.

The off-bus/configuration-zero iPad state, continued external power and pinned Wi-Fi SSH, Mac USBMux/raw USB disappearance, and return of data after a new boot point to the device-side USB controller lifecycle. They do not fit a mere Mac pairing, ChatGPT USB-client, or cable-recognition failure. The failed runs' changed `BcdUSBVersion`/`MPS0` registry values are observed with the off-bus state; the evidence does not show whether those values caused it or resulted from incomplete enumeration.

**Confidence:** The v3/v4 constructor-path difference is strongly supported by the controlled normal-trial comparison, while the object's internal difference is unknown. The missing first-enumeration gate in v5 is directly confirmed in source, and an early second transition is plausible from the event sequence; its role in the hardware failure remains unproven because the post-v4 starting state also changed. The current evidence cannot assign a single root cause to v5 without another discriminating observation or trial.

**Offline verification:** The Mac-only native settled-recovery fixture passed for both worker death and watchdog restart when run with local Unix-socket permission; it checks the five-second wait using a fake file-backed controller. `git diff --check` and Python compilation of the read-only comparison probe and host wrapper passed. The live read-only comparison probe passed full external checks before and after. None of these checks publishes a new USB description on the iPad.

A registry state check cannot by itself prove Mac USBMux, pairing, NCM, or exact live description recovery, and a first publication that never enumerates would still require a separate recovery decision.

## How to avoid another unnecessary restart

Keep controller trials stopped while this distinction is unresolved. The v5 postreboot boot was clean and USB healthy, but the later v7 worker-death trial left the **current** boot off bus with an active unverified journal.
