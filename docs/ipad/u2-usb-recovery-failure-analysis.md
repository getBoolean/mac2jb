# U2 USB recovery failure analysis

**FIRST SAME-BOOT USB RECOVERY, 2026-10-31:** On the failed second-v8 boot, the bounded re-publication loop had left 15/16 functions registered with only `Valeria` missing. The owner ran `host/recover-u2-restart-function-owner-wifi.py com.apple.audiomxd` (one `launchctl kickstart -k system/com.apple.audiomxd`; evidence `build/ipad-hardware/u2-trials/owner-restart-audiomxd-1793434837082550000/`). The syslog showed `register function Valeria`, and the controller immediately went `configured/OnBus=yes/config=5`. Independent read-only checks then passed: Mac USBMux one device at configuration 5, raw iPad node, `idevicepair validate` success, pinned mobile/root SSH, live `BcdUSBVersion/MPS0=784/9`, and a 44-node XDCI function census **identical** to the healthy-boot reference. **This confirms the mechanism:** after a description swap the XDCI controller goes on bus only once all 16 functions have re-registered (`gated_registerFunction`). Each swap leaves a random one or two unregistered because they race the old instances held by function owners (`audiomxd` for Valeria and audio user clients, `accessoryd` for the iAP port, kernel audio). Restarting the owner of the remaining unregistered function completes registration. **Working recovery recipe:** (1) read the swap's `register function` lines from network syslog; (2) if functions owned by kernel-only drivers are missing, re-publish (`restore-after-failure`) until only user-space-owned functions are missing; (3) restart those owners (`audiomxd` for Valeria and audio). The full external USB/NCM/descriptor comparison and journal confirmation are still pending, and a no-op trial must still pass this automatically for U2. A runner should automate steps 1–3 and avoid the broker jetsam kill (prepared fix: `host/update-u2-v8-jetsam-wifi.py`).

**Root-cause evidence from network syslog, 2026-10-31 (second v8 trial):** `idevicesyslog -n` captured the swap (`build/ipad-hardware/u2-trials/run-v8-1793432123603082000-86227e39/syslog.txt`). The kernel recreates all interfaces (`IOUSBDeviceController::createUSBDevice`), then each function registers (`gated_registerFunction: register function <name>`). **Only 14 of 16 registered after the trial publication** (missing `IapOverUsbHid`, `USBAudio2StreamIN`), and again 14 after the first Wi-Fi re-publication (missing `Valeria`, `USBAudio2StreamOUT`). There is no further controller message, and the controller stays off bus. At the swap the accessory manager logged `Can't reserve port ID 2 - port ID already reserved!`, so the new iAP `IOAccessoryPortUSB` raced the old one. `AppleUSBDeviceAudioController` logged a "USB Sound assertion" (lines 772/779), and the old `ptpd` crashed (corpse report `ptpd-2026-10-31-023536.ips` on the iPad). The relaunched `ptpd` attached to PTP normally and exited only after `waiting: 10s for host connection` timed out, so it is an effect, not the cause. **Mechanism (strongly supported):** the controller goes on bus only after every function in the description registers. A description swap races the old function instances held by `accessoryd`/`audiomxd`, a random one or two fail to register and are never retried, and the controller waits forever. Rare success fits winning the race; reboot recovery fits a fresh registration of all functions.

**Bounded re-publication loop (`host/recover-u2-until-registered-wifi.py`):** attempts 1 and 2 each re-published and registered 15/16 functions (missing `USBAudio2StreamOUT`, then `Valeria`); USB stayed absent. Attempt 3 did not publish: the v8 broker was killed by jetsam (`exceeded mem limit: InactiveHard 18 MB`) after repeated publications, and launchd restarted it in `recoveryRequired`. That is a broker robustness bug to fix (memory per publication, or a launchd jetsam limit). The controller therefore remains in attempt 2's state with **only `Valeria` unregistered**. Valeria is opened by an `audiomxd` user client, so `host/recover-u2-restart-function-owner-wifi.py com.apple.audiomxd` (one `launchctl kickstart -k`, no controller or journal action) is the targeted next step. The agent's tool policy blocked it, so it awaits the owner.

This is consistent with iOS launch constraints killing a platform daemon not spawned by launchd, so a manual start cannot test the PTP-owner hypothesis. **Superseded mechanism (refuted 2026-10-31, see kickstart result above):** `SetDescription` replaces every interface nub. `ptpd`, which held the old PTP nub, shuts down cleanly. The replacement PTP nub's IOKit match event either reaches the exiting `ptpd` or arrives before launchd re-arms the stream, so it is consumed and lost. `ptpd` exits with status 0 and launchd does not relaunch it. PTP is in every host-visible configuration except the locked audio one, and its class 6/1/1 interface is defined by the userspace owner, matching the open/configure/commit pattern in Apple's historical `restored_external.c`. Without the owner's commit the controller plausibly never asserts `OnBus`. That explains no Mac attach attempt, the failure of every controller, bus, force-off and replug action, nondeterministic success (who wins the exit/match race), and recovery only by reboot (fresh boot-time match). The healthy census's two `IOUSBDeviceInterfaceUserClient` instances are consistent with `audiomxd` on Valeria plus `ptpd` on PTP.

**Discriminating recovery candidate:** one `launchctl kickstart system/com.apple.ptpd` on this boot. If `ptpd` attaches to the PTP nub and the controller goes on bus with a Mac arrival, the mechanism is confirmed and the restore design must re-launch or wait for function owners after `SetDescription`. The guarded one-shot is `host/recover-u2-kickstart-ptpd-wifi.py`. It requires the recorded off-bus state, an unserved PTP nub and a stopped `ptpd`, starts the passive Mac observer, issues the single kickstart, and re-reads both censuses. It does not touch the controller, journal or broker. **It has not run:** the agent's tool permission policy blocked the remote write, and it awaits the owner running it directly.

**Function-provider reading of the census:** The 16 direct `IOUSBDeviceInterface` children are the 16 unique interface names across all nine configurations, so the controller publishes nubs for every configuration, not only the selected one. ## Why v1–v3 differ from v4

The most informative comparison is v3 versus v4. Both began with a 16-field original live description, used the same 3-second normal worker lifetime, called `SetDescription` followed by the explicit bounded bus cycle, and passed current-boot external prechecks. The selected description construction path changed: v3 rebuilt from defaults and patched four visible fields; v4 cloned the active controller description. Adding `GoOffAndOnBus` by itself was insufficient (v2 versus v3).

The exact internal reason is not exposed by the retained evidence. After adding the four known live-only values to the defaults object's info dictionary in memory, its 16-field dictionary was also `CFEqual` to the clone's. ## Why v5 may differ from v4

V5 changed two variables at once:

1. **Recovery timing.** The v4 normal worker remained alive for 3 seconds after publication. The v5 fault client called `os._exit(17)` immediately after receiving `OK published`, and the watchdog's `workerClosed` path synchronously called `recover()` with no first-enumeration readiness check (`u2-native-noop-trial-client-v5.py`, `NativeUSBWatchdogService.swift`, `USBRestoreCoordinator.swift`). The `OK published` reply follows API success, not an external arrival. Both publication and recovery call `SetDescription` and `GoOffAndOnBus(1000)` in `USBRestoreControllerShim.c`. The [Apple-authored historical controller header](https://github.com/nabla-c0d3/iphone-dataprotection/blob/master/ramdisk_tools/IOUSBDeviceControllerLib.h) describes a delayed return to the bus after `GoOffAndOnBus`; a successful return from the API does not document completed host enumeration. In v4, the first Mac arrival preceded the second termination by only 35 ms; in v5, no arrival was recorded. The v5 journal reached `awaitingVerification` near the first termination. An early second bus transition is therefore a concrete, source-backed failure mechanism, but the retained trace lacks a timestamp for the recovery call and cannot prove the transition preceded a would-be first arrival. A Mac-only fake-controller test passes with the offline v6 candidate's five-second delay for both worker death and watchdog restart. It proves the delay is taken, not that this iPad enumerates or recovers.
2. **Starting opaque state.** V4 began from the original stock description. V5 began from v4's post-replacement 17-field state. Its external precheck passed and its journaled 16-field dictionary is value-equal to the original pre-v4 dictionary; the extra live field was only `AllowMultipleCreates`. Nonetheless, `CreateFromController` may clone opaque state that changed during v4. The v5 in-memory validator checked visible info values, not a complete internal function-binding equivalence.

The v5 Mac lifecycle window had no arrival, and the iPad later read `disconnected/onbus=no/config=0` while Wi-Fi SSH and power remained. Mac USBMux logs recorded failures/detach without a specific controller error. On this recovered iPad, no accessible `log`, `syslog`, or `dmesg` CLI was found in the checked paths to retrieve a prior-boot controller trace. The retained data cannot separate timing from the post-v4 opaque state. Claiming that either alone caused v5 would overstate the evidence.

The off-bus/configuration-zero iPad state, continued external power and pinned Wi-Fi SSH, Mac USBMux/raw USB disappearance, and return of data after a new boot point to the device-side USB controller lifecycle. They do not fit a mere Mac pairing, ChatGPT USB-client, or cable-recognition failure. The failed runs' changed `BcdUSBVersion`/`MPS0` registry values are observed with the off-bus state; the evidence does not show whether those values caused it or resulted from incomplete enumeration.

**Confidence:** The v3/v4 constructor-path difference is strongly supported by the controlled normal-trial comparison, while the object's internal difference is unknown. The missing first-enumeration gate in v5 is directly confirmed in source, and an early second transition is plausible from the event sequence; its role in the hardware failure remains unproven because the post-v4 starting state also changed. The current evidence cannot assign a single root cause to v5 without another discriminating observation or trial.

**Offline verification:** The Mac-only native settled-recovery fixture passed for both worker death and watchdog restart when run with local Unix-socket permission; it checks the five-second wait using a fake file-backed controller. `git diff --check` and Python compilation of the read-only comparison probe and host wrapper passed. The live read-only comparison probe passed full external checks before and after. None of these checks publishes a new USB description on the iPad.

A registry state check cannot by itself prove Mac USBMux, pairing, NCM, or exact live description recovery, and a first publication that never enumerates would still require a separate recovery decision.

## How to avoid another unnecessary restart

Keep controller trials stopped while this distinction is unresolved. The v5 postreboot boot was clean and USB healthy, but the later v7 worker-death trial left the **current** boot off bus with an active unverified journal. The offline v6 five-second delay is a candidate, not an established fix; simply staging and running it from a post-clone state would repeat the v5 confounder. Before any future fault trial, the recovery design needs an observable first-enumeration condition or equivalent verified controller readiness check, a bounded failure path, and a way to distinguish API success from external USB recovery. A fixed delay alone does not establish those conditions. No verified headless command is known to restore data once this controller is off bus; in the earlier failed trials, a new boot was the observed recovery. Another speculative `SetDescription` or bus cycle could add a failure rather than avoid a restart.

If a further hardware trial is authorized, the most informative single trial is **v4 clone plus worker death from a fresh 16-field stock state**, with the exact original v4 binary/client, durable journal, pinned Wi-Fi SSH, passive Mac lifecycle monitor, and full external pre/post checks. It changes worker-close timing relative to the successful v4 normal trial while holding constructor path and starting live shape fixed. A failure would show early worker death is sufficient to break recovery even from stock state; a pass would shift attention to v5's post-v4 state or v5-specific code. Either outcome still needs the journal-preserving recovery procedure and may require a physical reboot/re-jailbreak if USB data does not return. Do not run it under the current instruction to identify the issue before another iPad trial. A subsequent v5-specific test should be considered only after that result, with one variable changed at a time.

For the final U2 gate, require a no-op round trip and worker/watchdog fault cases to restore the exact required live state and all externally checked USB functions without owner intervention. A watchdog `awaitingVerification` phase or a postreboot recovery check cannot substitute for that proof.
